# Meta integration

## Setup

1. Apply all migrations, including `028_meta_integration.sql` and `031_meta_delivery_diagnostics.sql`, with `pnpm db:migrate`.
2. Open `/admin/meta` as an owner. Managers can inspect configuration and delivery records; fulfilment accounts cannot access this page.
3. A Pixel/dataset ID enables browser events independently. Add a Conversions API token for server events. An ad account ID and a separate `ads_read` token enable advertising reports on the main dashboard.
4. Tokens use the existing `APP_ENCRYPTION_KEY` AES-256-GCM encryption. Blank token inputs preserve saved tokens; removal checkboxes delete them. No token or ciphertext is passed to the browser. A failed connection check does not falsely mark configuration as verified.
5. Keep `pnpm meta:worker:deploy` running in production (after `pnpm build:deploy`). The Docker Compose deployment includes `meta-worker`. Local `pnpm dev` starts the same worker inside the development server through Node instrumentation, with one instance per process across hot reloads; opening delivery health also starts it on development servers launched before instrumentation was added. It stops with the development server. `pnpm meta:worker` remains available for a separate local worker. Request completion also attempts prompt delivery; the durable worker recovers missed callbacks and verifies paid orders independently of checkout requests.

The setup guide at the bottom of the page explains where to find IDs, how to generate tokens, asset permissions, Test Events, the production domain, and deduplication. Configuration is read from the database, with no redeploy required. Existing storefront tabs refresh settings on focus and every 60 seconds.

## Events and financial meaning

- `PageView`: storefront route navigation after marketing consent.
- `ViewContent`: a product or bundle page; uses its active default variant, matching N7's checkout model.
- `ViewCategory`: a collection, bundle listing or active collection category page. The server resolves the listing name and up to ten eligible catalogue variant IDs; the Pixel uses `trackSingleCustom`, and CAPI shares the same name and event ID for deduplication. Known customer hashes are included through the same manual matching path as other events.
- `Search`: a completed storefront search response. Search text is deliberately omitted.
- `AddToCart`: successfully validated additions or quantity increases, not failed attempts.
- `InitiateCheckout`: entering checkout with products, or starting express checkout from the basket.
- `AddPaymentInfo`: successfully creating/reusing a Stripe checkout before payment confirmation. No card information is collected by this integration.
- `Purchase`: a verified paid Stripe order; pending, failed, cancelled and historical orders are excluded. Values are GBP paid order totals after discounts, including shipping/tax. Item values use the stored discounted line totals. Revenue is a purchase value, not profit or net-of-refund revenue.

Browser/server copies share event name and ID. Purchase IDs are `n7_purchase_<order ID>`. Catalogue content IDs are `n7_variant_<variant ID>`, including the bundle variant (not its component stock reservations). Future catalogue exports must use this same helper. A variant ID is a string, including IDs above JavaScript's safe integer limit.

Public clients cannot post `Purchase` events or supply prices. Event products/prices resolve from N7's database. Checkout credentials and Stripe secrets are stripped from receipt URLs and retained only in tab session storage for receipt refresh. If storage is blocked or the document/referrer contains sensitive query parameters, the browser Pixel is suppressed; eligible server events continue. The browser receipt event requires the same consenting browser as the original checkout.

Optional attribution writes use a database savepoint so a Meta storage/encryption failure does not undo a valid checkout. If the database itself aborts the order transaction, normal checkout rollback still applies. Failed attribution is omitted instead of reconstructing customer tracking data later.

## Consent and privacy

No Meta script, click cookie, tracking request or server event is enabled before explicit marketing consent. The footer provides a permanent preference control. Newsletter permission is separate. The server stores an opaque HttpOnly preference cookie and verifies consent again at collection, purchase processing and delivery. Withdrawal cancels pending events and removes order tracking contexts. Already transmitted/in-flight events cannot be recalled.

Consenting checkouts supply normalized SHA-256 hashes of email, phone, billing first/last name, city, region when supplied, postcode and ISO country. GB local phone numbers are normalized to the country calling code; one-word names omit the unknown surname. A hashed visitor ID derived from the opaque consent ID stays consistent across server browsing, checkout and Purchase, and is included in Pixel matching once contact data is known. Only the encrypted, already hashed checkout profile is retained with this browser's valid consent for up to 180 days. Subsequent consenting server events, including ViewContent, can reuse it. Anonymous visitors do not supply invented contact fields; withdrawal or expiry removes the profile, and renewal does not revive expired details.

Each browser event response carries the server's canonical hashed External ID and any known, validated customer hashes, including county/region (`st`). The [current Pixel SDK](https://connect.facebook.net/en_US/fbevents.js) accepts another `init` only while its existing user data is empty. Anonymous Pixel initialization therefore uses an empty matching object; seeding only `external_id` would lock out contact data entered later in checkout. The first known email/phone profile upgrades Pixel with its available customer hashes and canonical External ID. Returning visitors with a known profile initialize with those hashes immediately. Identical later profiles do not reinitialize Pixel. Anonymous browser/server events still share event IDs for deduplication and use the normal browser/click cookies.

Once that document has a nonempty Pixel matching profile, additional fields are used by CAPI and by Pixel on the next full page load; repeated `init` cannot add them. If an existing hash or consent identity changes, the browser event is suppressed until a full page load rather than inheriting the SDK's stale buyer details. Eligible CAPI events continue with the current profile. Missing/invalid consent IDs also block browser delivery. The server queue applies the canonical ID to every event associated with consent, preserving it across retries. Matching fields never enter commerce/custom-data parameters.

Checkout now updates manual matching when a valid email and available billing contact/locality details are known, after a one-second pause in editing. Saved details follow the same consent checks. Express card/wallet checkout supplies its confirmed buyer details through the shared payment path, independently of payment completion. `/api/meta/matching` accepts only bounded, validated contact fields from the same origin, rate-limits requests and locks the current consent row before retaining encrypted hashes. It creates no tracking event or purchase. Successful unchanged updates are deduplicated; pending writes are serialized and late responses after withdrawal or an identity change cannot initialize Pixel. Matching failures never block payment. Browser storage receives no new contact data.

The optional county/region field is visible alongside the main checkout address fields; wallets supply their actual address state when available. Consenting Pixel-only checkouts also retain the encrypted matching profile, independently of CAPI. A later checkout omitting county preserves its known hash only when email, name, city, postcode and country still match; changing the buyer or locality clears it. No county is inferred from IP, town or a partial postcode, and no placeholder value is sent for an unknown county. Anonymous visitors without a known address will still have no county parameter, so 100% coverage is not expected.

IP, browser user agent, `_fbp` and `_fbc` are passed unhashed per Meta's field definitions. Traefik trusts forwarding only from Cloudflare's published IPv4/IPv6 ranges. The application accepts Cloudflare's client-IP headers only when the final proxy in Traefik's forwarding chain is a verified Cloudflare edge; genuine `CF-Connecting-IPv6` takes precedence when Pseudo IPv4 overwrites the normal headers. Direct-origin spoofed Cloudflare headers are ignored. Keep the ranges in `lib/http/client-ip.ts` and the production compose file synchronized with https://www.cloudflare.com/ips/.

The actual landing `fbclid` and arrival time are held in tab memory across storefront navigation; `_fbc` is written only after consent. Denial clears that memory. A temporary settings-fetch failure pauses tracking without discarding the landing click. Street addresses, notes, card data and search text are excluded. Gender and date of birth are not collected. Browser automatic configuration is disabled; do not enable additional automatic events/advanced matching in another Pixel installation.

Queued events and checkout attribution snapshots are encrypted. Accepted/failed/cancelled job payloads are erased. Delivery retries expire at 47 hours to stay inside the 48-hour browser/server deduplication window. Checkout attribution snapshots expire after two days. Queue metadata expires after 30 days. Minimal per-order status/reasons and timestamps remain with the order, without cookies, matching data or event payloads; deleting the order cascades its diagnostic record. The worker performs cleanup; it must remain running even when tracking is paused.

Browser purchase deduplication markers expire after 47 hours and are cleaned on the next settings refresh, or immediately when consent is withdrawn. A local opt-out takes precedence over stale server consent, including when local storage is unavailable; failed withdrawal requests are retried on subsequent settings refreshes.

## Testing and operation

Order detail pages show server Purchase status, the actual capture/skip reason, attempt count and delivery timestamps. The migration preserves existing checkout contexts and retained Purchase proof; reasons for older untracked orders remain unknown. `/admin/meta` shows a five-minute worker heartbeat, recent credential/delivery errors and an explicit server-test-mode warning. Browser event requests retry transient failures up to three attempts using the same ID and stop when consent changes. Pixel script loading makes at most two attempts. Common campaign parameters are allowed; receipt/payment credentials still suppress browser Pixel activity.

Delivery health refreshes every 30 seconds and on focus through an owner/manager-only, uncached endpoint. Worker freshness uses the database clock and actual heartbeat rather than page-open time or the last successful API request. Waiting jobs and recent failures remain prominent. Older terminal failures appear separately as retained history; their already-erased payloads are not reconstructed or replayed. The current saved CAPI token is checked for decryptability independently, so an old failed event cannot falsely report that the current encryption key is broken. Counts and delivery records use the currently configured dataset. Times use UK time consistently with catalogue status.

`pnpm test:unit`, `pnpm meta:verify-flow` and `pnpm payments:verify-flow` are non-browser checks. The integration scripts use disposable local databases and mock outbound API calls; they do not send real events or charge cards.

For an authorised live check, save a Test Events code and select **Send server test event**. Only a synthetic `PageView` with that code is sent. Test payments are server-only and require this code; they never trigger browser Purchase events. Browser activity still uses the saved Pixel, so use a dedicated test dataset when testing the complete browser journey. Remove the code before production server reporting. Review Meta Test Events, Diagnostics, Event Match Quality, and browser/server deduplication yourself before launch.

Meta API errors are reduced to safe messages/numeric codes. Transient failures retry with exponential backoff. Invalid credentials/permissions require an owner to fix the connection. Delivery statuses indicate whether Meta accepted a request, not whether it attributed a purchase to an ad. The dashboard's Traffic and Meta ads tabs read account, daily, campaign and delivery-breakdown reports, with one-minute caching and explicit attribution. Spreadsheet catalogue export remains separate future work. See [dashboard definitions](dashboard.md).

If Events Manager recommends **Set up manual advanced matching**, verify email/phone fields on a recent **browser** event from a consenting first-time checkout, not only a returning visitor or server event. Code presence and passing command-call tests do not establish that the SDK applied matching data. Check the recommendation's affected URLs and last-detected time if it persists despite recent browser contact fields; there is no guaranteed clearance time assumed by this integration. Anonymous visits have no invented contact details. **ViewCategory — No recent activity** requires new consenting visits to collection/category listings after deployment; old events and matching coverage do not change retroactively.

Both tabs include matching-parameter coverage filtered by their applied report period and account timezone. Only accepted live events for the configured dataset count; tests, failures and other datasets are excluded. The report retains boolean field-presence flags with queue metadata, never the values. Percentages exclude older accepted events whose coverage was not recorded, displaying the measured and accepted counts. Queue retention still limits historical coverage to 30 days. These percentages are not Meta Event Match Quality scores.

## Automatic product catalogue

Migration `033_meta_catalog_sync.sql` adds the durable catalogue queue and connection state. Deployment applies it before starting the updated application and shared `meta-worker`; no new service is required. Catalogue settings are independent of the existing Pixel, Conversions API and reporting settings. No credentials means no catalogue API requests.

In **Admin → Meta → Automatic product catalogue**, an owner saves the catalogue ID and a system-user token assigned to manage that catalogue. Find the ID in Commerce Manager's catalogue settings. In Business Settings, assign the catalogue to the system user, create its app token with `catalog_management`, and grant any business permissions required by the app/assets. Meta can require app review or business verification depending on asset ownership and access. Tokens are encrypted, never returned to the browser and preserved when their field is blank. Changing a saved catalogue ID without supplying a new token clears the previous token. Managers can view status; only owners can save or request operations.

Enable the connection and use **Check catalogue access**. This checks the saved ID, ecommerce catalogue type and read access; the first successful product batch verifies write access. **Sync now / retry failed** requests reconciliation, including eligible failed items. Pausing stops outgoing catalogue operations and keeps items already in Meta. The worker resumes against the latest saved settings.

The shared Meta worker checks for product changes every 30 seconds and submits batches of up to 50 items. Catalogue polling runs independently of conversion delivery, so a busy conversion queue does not delay catalogue checks. Meta processes batches asynchronously: submission handles are shown as processing, and items become **Confirmed synced** only after every returned handle confirms completion without errors. Admin status refreshes every 30 seconds. Temporary submission failures retry with backoff, up to eight attempts; temporary polling failures retain the original handles. Permanent failures require corrected credentials/details and **Sync now / retry failed**, including failed removals of deleted products. A catalogue lease prevents overlapping workers; interrupted submissions recover using the same IDs. A daily full reconciliation restores the integration's eligible products if their remote values were changed or removed.

Migration `034_meta_catalog_observations.sql` preserves the existing sync records and adds independent Meta product observations. **Product data synced** means the batch was confirmed; the **Meta images & ad eligibility** section separately displays image fetching, ad review and product issues returned by Meta. Product codes precede names in the searchable, paginated results, and each item shows its actual check time. Error descriptions are rendered as plain text; API tokens and raw credential errors never reach the browser.

The worker reads status every 30 seconds using `products` filtered to this integration's managed IDs, with at most 100 items per cycle and 50 IDs per request. Large catalogues rotate through the least recently checked items. The admin's protected status endpoint can also schedule a due read; a database lease and interval prevent duplicate requests across workers/viewers. No uploads or product removals are triggered by a status read. Polling uses Meta's `image_fetch_status`, `errors`, `capability_to_review_status` for `DA` (catalogue ads), and review fields. An image being fetched or a shop review being approved does not establish ad eligibility. Only explicit ad approval, the current image being ready and no blocking errors count as eligible; `NO_REVIEW`, unknown values and absent ad approval stay unconfirmed. Meta's missing/invalid image error remains visible even when image fetch status is `NO_STATUS`.

Observations are bound to the saved credentials and exact confirmed product payload. Results from before an edit, from different credentials or older than two minutes are excluded from current eligibility counts. API errors, malformed responses and incomplete pagination retain the previous check timestamps and show the failed check; they never fabricate approval or a mass missing-product result. Complete reads can report a managed item missing from Meta. Pausing the connection pauses remote reads. These are automatically polled results, not an instantaneous push stream; the page refresh interval can add up to another 30 seconds after a worker check.

Only published products with an active default variant are included, matching the current storefront's purchasable variants. IDs are exactly `n7_variant_<variant ID>`, shared with Pixel/CAPI events, and `item_group_id` is `n7_product_<product ID>`. Product codes precede names. Standard products and bundles use their public HTTPS storefront URLs, actual images, descriptions and GBP unit prices. Checkout-only offers and compare-at prices do not become fictitious catalogue sale prices. `APP_URL` must be the public HTTPS website origin and image URLs must be publicly accessible.

Availability reuses storefront inventory calculations, including component quantities for bundles and stock already reserved by checkouts. Published sold-out products remain with **out of stock** availability. Stock quantities are omitted for untracked products. Products missing required catalogue details are excluded with a visible reason; if previously uploaded, they are removed until corrected. Unpublishing or deleting a managed product queues removal of that exact ID. A failed database scan cannot cause removal of all items. This integration never enumerates or deletes unrelated Shopify, WooCommerce or other-source IDs.

Before manually removing the old Meta data sources, confirm this connection's write access, a completed full sync and product ID matching in Commerce Manager. Retire obsolete sources and their old items manually, then connect the intended Pixel/dataset to this catalogue. Saving N7's connection does not remove old sources, migrate their IDs or grant product/ad approval.

`pnpm meta:verify-catalog` uses a disposable local database and mocked Meta responses to verify inventory, IDs, asynchronous confirmation, concurrent workers, retries, pause/resume, product deletion and scanner failure. It sends no real Meta requests. The deployment quality checks run it alongside the existing Meta delivery checks.

The same verification covers status leases, unknown approval, Meta image errors, stale data, credential changes, concurrent product edits, malformed/incomplete responses, API outages and recovery. Release verification checks that migration 034 preserves existing catalogue items and initializes their new observations as unknown. Current status fields were checked against Meta's [official ProductItem SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/productitem.py) and read-only responses from the configured live catalogue on 2026-10-07.
